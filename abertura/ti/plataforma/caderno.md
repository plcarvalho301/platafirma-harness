## Conhecimento curado

- Promover código de uma unit de usuário (systemd --user) NÃO basta com `release promover`: ele materializa `current` e recria containers de STACK, mas não recarrega units de usuário. O systemd exige `systemctl --user daemon-reload` quando o `.service` mudou no disco, e `infra restart` não o faz — reexecuta o ExecStart mas o systemd mantém a definição velha em memória. Sintoma: unit segue no código antigo após promover + restart pela porta; o journal não registra start novo. Prova é medir o efeito, não confiar no "reiniciada: active" do verbo. Cura hoje é ato no host (fora da porta): `sudo -u <conta> XDG_RUNTIME_DIR=/run/user/$(id -u <conta>) systemctl --user daemon-reload && ...restart <unit>`. Mesma classe do pf-porta-watch que não reinicia a porta após promover.

- Sonda de leitura que passa por `sessao abrir` cunha chave viva no msg-mem como efeito colateral — leitura com escrita escondida. Prova de disponibilidade de montagem deve usar leitura pura (`expediente montar --sem-acervo`), nunca `sessao abrir`/`monta-sessao`. Padrão a imitar: sondas infra_estado/conferir_* do agregador não cunham nada.

- Stack de código (harness) e código servido pela PORTA sobem por caminhos diferentes: stack por `deploy promover` (recria container), verbo servido pela porta pela promoção do harness + reinício da porta. Mudança em bin/<verbo> só chega ao que a sessão executa quando o harness é promovido; até lá a porta serve o código velho, mesmo com o PR já em main. Não confundir "mergeado em main" com "servido". E "servido pela porta" ainda não é produção do que o RUNTIME lê de arquivo publicado: `release promover` também republica a abertura (dono.md, persona.md) em /srv/.../abertura-publicada/current/abertura; código que lê esse caminho (ex. _sha_publicado) só vê a versão nova após a promoção, não após o merge.

- Um mecanismo dormente (gancho no-op guardado "caso precise") que já provou levar a deriva é dívida, não conveniência: mantê-lo deixa disponível o desvio que causou o problema. O pre_build (andaime da wiki, #3075) era isso — removido quando nenhuma stack o usava. Régua: gancho que só existe para um caso já eliminado sai junto com o caso.

- Worktree só se remove depois de conferir que não tem trabalho a perder — e a régua "poda só o que já subiu" tem um caso traiçoeiro: branch com upstream `[gone]` (remoto apagado) MAIS commit à frente de origin/main = o commit é a única cópia fora do reflog; `worktree remove` o perde para sempre. Confirmar com `git status -b` (vê o [gone]) e `git log origin/main..HEAD` (vê o commit não-mesclado) ANTES de remover. Se houver commit órfão, resgatar primeiro: `git push origin HEAD:refs/heads/resgate/<slug>` põe o trabalho a salvo no remoto; só então remover o worktree. Nome de worktree com UUID em vez de cadeira é sinal de fita que não limpou — mas nome feio não autoriza remover sem conferir o conteúdo. Untracked puro (só `??` no status, `git clean -nd` confirma) é lixo de bancada e limpa com `git clean -fd`.
